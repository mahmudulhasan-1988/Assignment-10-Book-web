# Delivery Request Feature - Implementation Plan

## Context
The Book Detail Modal has a "Request Delivery" button that is currently non-functional. The project uses MongoDB (via better-auth) but has no delivery API routes or collection. All data is currently mock. The user wants full API + MongoDB persistence.

## Architecture
- **Database**: Reuse the existing MongoDB connection from `src/lib/auth.js`
- **API Routes**: Next.js App Router route handlers under `src/app/api/deliveries/`
- **Client**: React Context for shared state + `fetch()` calls to the API
- **Auth**: Use `useSession()` from better-auth to identify the requesting user

## Files to Create

### 1. `src/lib/mongodb.ts` — Shared MongoDB connection
- Export a singleton `getDb()` function that returns the MongoDB `db` instance
- Reuse the same `MONGODB_URI` and `DB_NAME` env vars from auth.js
- Avoids creating multiple connections

### 2. `src/app/api/deliveries/route.ts` — Delivery API
- **GET**: Fetch deliveries (filtered by `?userId=` query param, or all for librarians)
- **POST**: Create a new delivery request
  - Body: `{ bookId, bookTitle, bookAuthor, bookCover, deliveryFee }`
  - Reads user from session (via `auth.api.getSession()`)
  - Creates delivery document with status "Pending", timestamp, user info
  - Returns the created delivery

### 3. `src/components/books/DeliveryRequestModal.tsx` — Request confirmation modal
- Opens when "Request Delivery" is clicked
- Shows book cover, title, author, delivery fee
- Shows estimated delivery date (2-3 days from now)
- "Confirm Request" button → POST to `/api/deliveries`
- Shows loading spinner during request
- Shows success state with checkmark after confirmation
- Shows error state if request fails
- "Cancel" button → closes modal

### 4. `src/lib/delivery-context.tsx` — Client-side delivery state
- React Context that caches deliveries fetched from the API
- `fetchDeliveries(userId?)` — GET from API
- `addDelivery(delivery)` — optimistic update after POST
- Used by DeliveryHistoryTable and ManageDeliveriesTable

## MongoDB Delivery Document Schema
```js
{
  _id: ObjectId,
  userId: string,          // better-auth user ID
  userName: string,        // user's display name
  userEmail: string,       // user's email
  bookId: string,          // book ID
  bookTitle: string,       // book title
  bookAuthor: string,      // book author
  bookCover: string,       // cover image URL
  deliveryFee: number,     // fee amount
  status: "Pending" | "Dispatched" | "Delivered",
  requestDate: ISO date,
  updatedAt: ISO date
}
```

## Data Flow
```
1. User clicks "Request Delivery" in BookDetailModal
2. DeliveryRequestModal opens with book details
3. User clicks "Confirm Request"
4. POST /api/deliveries with book data
5. API reads session, creates delivery document in MongoDB
6. Returns created delivery to client
7. Client shows success toast
8. DeliveryContext updates state
9. DeliveryHistoryTable re-renders with new delivery
10. Librarian's ManageDeliveriesTable also shows the new request
```
